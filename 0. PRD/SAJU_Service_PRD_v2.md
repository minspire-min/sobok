### 3.6 R6. 부족 오행 판정 — 점수제

**점수표** (8칸, 합계 100점)

| | 시주 | 일주 | 월주 | 연주 |
| --- | --- | --- | --- | --- |
| 천간 | 10 | 10 | 10 | 10 |
| 지지 | 15 | 15 | **20** | 10 |

**연속 가중치 ×1.3 — "덩어리" 방식 (확정)**

1. **위·아래(같은 기둥의 천간↔지지)** 또는 **왼쪽·오른쪽(이웃 기둥의 같은 줄)** 으로 이어진 같은 오행 칸들을 하나의 **덩어리**로 묶는다
2. 2칸 이상 이어진 덩어리는 **칸 점수 합계 × 1.3** (덩어리당 1번만)
3. 떨어져 있는(이어지지 않은) 같은 오행 칸은 ×1.3 없이 그대로 더한다
4. 오행별 합계가 **가장 낮은 오행 = 부족한 오행**. 개수 0인 오행은 0점이라 자동으로 최저 → "0인 오행" 규칙도 이 하나로 처리됨
5. 시간 미상: 시주 2칸 제외 (75점 만점)

**확인 예시 1** — 천간 `계 계 을 계` (시·일·월·연)

- 시간 癸 – 일간 癸: 이어짐 → (10 + 10) × 1.3 = 26
- 월간 乙(목)이 사이에 끼어 연간 癸는 떨어져 있음 → 10
- 천간의 수 점수 = **(10+10)×1.3 + 10 = 36**

**확인 예시 2** — 시 丙寅 / 일 甲子 / 월 己卯 / 연 乙卯

| | 시주 | 일주 | 월주 | 연주 |
| --- | --- | --- | --- | --- |
| 천간 | 丙 화 10 | 甲 목 10 | 己 토 10 | 乙 목 10 |
| 지지 | 寅 목 15 | 子 수 15 | 卯 목 20 | 卯 목 10 |

- 목 덩어리: 연간 乙 ↕ 연지 卯 ↔ 월지 卯 → (10+10+20) × 1.3 = 52
- 떨어진 목: 일간 甲 10, 시지 寅 15
- 목 77 / 화 10 / 토 10 / 금 **0** / 수 15 → **부족 오행 = 금**

**동점 처리 (확정)** — 최저 점수 오행이 2개 이상일 때

선택한 고민 카테고리와 **연관된 오행**이 동점 오행 중에 있으면 그 오행을 고른다. 연관 오행은 **일간(나) 오행과의 관계(십신)** 로 정한다.

| 관계 | 뜻 | 일간 기준 오행 | 일간이 수(水)일 때 |
| --- | --- | --- | --- |
| 재성 | 재물 | 일간이 **이기는**(극하는) 오행 | 화 |
| 관성 | 직업적 지위·통제력, (여자) 배우자 | 일간을 **이기는** 오행 | 토 |
| 인성 | 보호·안정·배움, 부모 | 일간을 **낳는**(생하는) 오행 | 금 |
| 식상 | 표현·활동, (여자) 자녀 | 일간이 **낳는** 오행 | 목 |
| 비겁 | 친구·동료·형제 | 일간과 **같은** 오행 | 수 |

| 고민 카테고리 | 연관 관계 | 비고 |
| --- | --- | --- |
| 재물/돈 | 재성 | 확정 (예시 기준) |
| 직장/커리어 성장 | 관성 | 확정 (예시 기준) |
| 취업/이직 | 관성 | 기본안 — 직장·지위 |
| 인간관계 | 비겁 | 기본안 — 친구·동료 |
| 마음/멘탈 | 인성 | 기본안 — 안정·보호 |
| 연애/결혼 | 여자: 관성 / 남자: 재성 | 기본안 — 전통 배우자 관계 (성별 사용) |
| 가족/육아 | 연관 없음 → 랜덤 | 기본안 — 부모(인성)·자녀(식상/관성)·형제(비겁)가 섞여 하나로 못 정함 |
| 건강 | 연관 없음 → 랜덤 | 기본안 |

**판정 순서**

1. 최저 점수 오행이 1개 → 그 오행
2. 동점 여러 개 + 카테고리 연관 오행이 그 안에 있음 → 연관 오행
3. 동점 여러 개 + 연관 오행이 없음(또는 연관 없는 카테고리) → 동점 오행 중 **랜덤 1개**
4. 결정된 오행 × 선택한 카테고리 → 부적 3종 (§3.7)

> 예: 일간 수(水), 화 0·토 0 동점 → 재물/돈 선택 시 **화**, 직장/커리어 성장 선택 시 **토**, 건강 선택 시 화·토 중 랜덤
>
> 랜덤 결과는 접수 시 서버에 저장해 **새로고침·어드민에서 바뀌지 않게** 한다.

**오행 분포 막대 (확정)**: 기존대로 **개수** 표시 유지. 점수·판정 근거는 어드민 상세에서만 보여준다.

### 3.11 R11. 어드민 페이지

#### 접근

| 항목 | 내용 |
| --- | --- |
| **진입 경로 (확정)** | **`https://mingming-saju.netlify.app/admin-mingminjimin`** — 제작자가 주소창에 직접 입력 (노트북 즐겨찾기). 참여자 화면에는 어드민으로 가는 **링크·버튼이 전혀 없다** |
| 진입 흐름 | `/admin-mingminjimin` 접속 → **아이디 + 비밀번호** 로그인 화면 → 통과 시 참여자 목록 |
| `/admin` 처리 | 어드민 화면이 아닌 일반 404(없는 페이지)로 보낸다 — 어드민 존재를 드러내지 않음 |
| 접근 제한 | **제작자만** — 서버에서 아이디·비밀번호 확인 (아래 "접근 차단 방법") |
| 계정 정보 보관 | 아이디·비밀번호는 **Netlify 환경변수(`ADMIN_ID`, `ADMIN_PASSWORD`)에만** 둔다. **이 문서·코드·깃허브 어디에도 적지 않는다** |
| 레이아웃 | 노트북/태블릿 폭 허용 (사용자 화면의 640px 제한 미적용) |

**왜 별도 사이트로 분리하지 않나**

| 이유 | 설명 |
| --- | --- |
| 결과 화면 "그대로" 재사용 | 상세에서 참여자 결과 화면을 똑같이 보여주려면 같은 계산 코드·화면 컴포넌트를 써야 한다. 사이트를 나누면 코드를 복사하게 되고, 한쪽만 고치면 두 화면이 어긋난다 |
| 같은 서버·저장소 | 같은 사이트의 서버 함수와 저장소를 그대로 쓴다. 나누면 사이트 간 데이터 공유를 따로 설정해야 한다 |
| 관리 1개 | 배포·환경변수·도메인을 한 번만 관리 |
| **보안은 주소가 아니라 서버가 지킨다** | 사이트를 나눠도 주소는 결국 알려질 수 있다. 데이터를 지키는 건 "서버가 비밀번호 없는 요청에 데이터를 안 주는 것"이다. 이건 같은 사이트든 다른 사이트든 똑같이 해야 한다 |

> 단점: 어드민 **화면 코드**가 사용자 사이트 파일에 함께 실린다(데이터는 아님). 어드민 화면은 따로 불러오도록(lazy load) 분리해 일반 참여자 화면에서는 내려받지 않게 한다.

**정리 — "주소는 나뉘어 보이지만 실제로는 한 사이트"**

| 구분 | 참여자 화면 | 어드민 |
| --- | --- | --- |
| 주소 | `mingming-saju.netlify.app/` | `mingming-saju.netlify.app/admin-mingminjimin` |
| 사이트(배포) | 같은 Netlify 사이트 1개 | ← 동일 |
| 코드 | 같은 프로젝트 폴더 | ← 동일 |
| 저장소·서버 함수 | 같은 저장소 | ← 동일 |
| 차이 | 누구나 접속 | **로그인한 제작자만 데이터를 받음** |

아파트 한 동에 공용 현관과 관리실이 있는 구조와 같다. 건물(사이트)은 하나지만 관리실 문(어드민)은 열쇠(로그인)가 있어야 열린다. 주소를 알아도 문이 잠겨 있으면 들어갈 수 없다.

**접근 차단 방법 (제작자 외 접근 불가)**

1. 로그인 화면에서 아이디·비밀번호 입력 → **서버**가 환경변수 `ADMIN_ID`·`ADMIN_PASSWORD`와 대조 (브라우저 코드에는 정답이 없음)
2. 맞으면 서버가 **브라우저 스크립트가 읽을 수 없는 로그인 쿠키**(HttpOnly, 12시간 만료) 발급
3. 모든 `/api/admin/*` 요청은 서버가 쿠키를 확인하고, 없으면 데이터 대신 거절(401)
4. 비밀번호 연속 실패 시 일정 시간 차단(예: 5회 실패 → 10분)
5. 검색엔진 노출 차단(`noindex`)
6. 고도화: 로그인 기능이 생기면 제작자 계정만 허용하는 방식으로 교체

**"이름/닉네임은 보내지 않는다"의 의미**

이건 **어드민 화면**이 아니라 **AI(Anthropic)에 보내는 요청 내용**에 대한 이야기다.

| 대상 | 보이는 정보 |
| --- | --- |
| 어드민 화면 | **전체 정보** (이름/닉네임, 성별, 생년월일시, 카테고리, 부적, 메모, 풀이 전부) — 우리 서버에서 바로 읽어 보여준다 |
| AI에 보내는 요청 | 사주 계산 결과(8글자·오행·십신·신살)와 고민 카테고리만. **이름은 빼고 보낸다** |

이유: 풀이를 쓰는 데 이름은 필요 없다. 필요 없는 개인정보를 외부 서비스로 보내지 않는 것이 안전하다(최소 전송). 풀이가 완성되면 우리 서버에서 해당 참여자 기록에 붙여 저장하므로 어드민에서는 이름과 함께 보인다.

## 4. 구조 — 서버 저장

### 4.1 흐름

```
[공용 기기]
  ① 입력 + 동의 → [확인하기] → 로딩 로티
  ② POST /api/submissions → 저장, id 반환
  ③ 결과 화면 (만세력 브라우저 계산) + 부적 3종 (테이블 조회, 즉시)
  ④ [선택 완료] → PATCH /api/submissions/:id { selectedTalismanId }
  ⑤ [입력 화면으로 돌아가기] → 기기 저장값 삭제 → 빈 입력 화면

[제작자 노트북]
  ⑥ /admin 로그인 → 목록 → 상세
  ⑦ 풀이 없으면 POST /api/admin/submissions/:id/reading (AI 1회) → 저장
  ⑧ 부적 변경 / 메모 저장 → PATCH

[매일 자동]
  ⑨ 접수 후 15일 지난 기록 전부 삭제
```

### 4.2 스택

| 역할 | 선택 |
| --- | --- |
| API | Netlify Functions |
| 저장소 | Netlify Blobs (대안: Supabase — 목록 검색·정렬이 많아지면) |
| 15일 삭제 | Netlify Scheduled Function (하루 1회 이상) |
| AI | Messages API + `ANTHROPIC_API_KEY` |
| 로딩 | `lottie-react` |

*(Netlify Blobs·Scheduled Functions 무료 한도는 배포 전 확인 — 미확실)*

### 4.3 저장 데이터

```
submission {
  id                    // 랜덤 UUID
  createdAt             // 15일 계산 기준
  consentAt
  nickname, gender
  calendarType, isLeapMonth, year, month, day
  hour, minute, timeUnknown
  category
  elementScores         // { 목, 화, 토, 금, 수 } — 판정 근거
  tiedElements          // ['화','토'] 최저 점수 동점 오행 (1개면 그 1개)
  lackingElement        // '화' 최종 결정 오행
  lackingReason         // 'lowest' | 'category' | 'random' — 어드민 판정 근거 표시용
  talismanIds[3]        // ['money-금-1', ...]
  selectedTalismanId    // null 또는 ID
  selectedBy            // 'user' | 'admin'
  selectedAt
  reading               // 간단 풀이 (생성 전 null)
  readingModel          // 'claude-sonnet-5-5'

```

### 4.5 배포 방식 — 깃허브 없이 Netlify만으로 되나?

**된다.** 단, 방법에 따라 서버 함수 포함 여부가 다르다.

| 방법 | 화면 | 서버 함수(저장·어드민·15일 삭제) | 비고 |
| --- | --- | --- | --- |
| ① 깃허브 연결 자동 배포 (현재 설정) | ✅ | ✅ | push하면 자동 배포. 변경 이력·되돌리기가 쉬움 |
| ② **Netlify CLI** (`netlify deploy --build --prod`) | ✅ | ✅ | 깃허브 없이 내 컴퓨터에서 바로 올림. 함수까지 함께 올라감 |
| ③ 웹에서 `dist` 폴더 끌어다 놓기 | ✅ | ❌ | **화면만 올라가고 서버 함수는 안 올라간다** → 이번 버전에서는 쓸 수 없음 |

- 이번 버전은 서버 함수가 핵심이라 **① 또는 ②**만 가능
- 현재 사이트가 깃허브 레포와 연결돼 있으므로, ②로 올린 뒤 나중에 깃허브에 push하면 **깃허브 버전으로 덮어써진다.** 한 가지 방식으로 통일할 것
- 내일 이벤트 기준 권장: **②로 빠르게 올리고**, 이벤트 후 정리해서 깃허브(비공개 레포)로 통일
- 환경변수는 어느 방식이든 Netlify 사이트 설정에서 등록
- *(예약 함수가 CLI 배포에서도 동작하는지는 배포 후 실제 실행 로그로 확인 — 미확실)*
